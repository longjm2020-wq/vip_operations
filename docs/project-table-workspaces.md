# Project table workspaces

Project tables reuse the selection controllers and service layer. Each table has a database schema named `selection_table_<validated bigint id>` containing selection rows, images, number claims, presence, shared view, protection and collection tables. Migration 029 provisions empty structures from the current public selection schema, preserving constraints and indexes and recreating foreign keys and triggers. Master data, users, audit and idempotency records remain public. Identity IDs use the public sequences so row, collection and audit IDs remain unique across tables. Original selection records remain in public.

The controller interceptor verifies the catalog ID before entering an AsyncLocalStorage scope. Transactions set a transaction-local search path; standalone SQL operations run in a scoped transaction too. No connection-pool session state or global current-table variable is retained. Idempotency operation names and pending sync keys include the workspace ID. Public collection requests derive their scope from the server-maintained token registry, never from the query parameter. Token rotation updates this registry atomically.

The frontend captures the API scope in a React provider with a separate QueryClient and per-table browser storage keys. Async saves retain the provider's scope after navigation. Mobile links preserve the scope during row changes; stored private image URLs include tableId. All protected API routes still use the existing authentication and selection permission checks.

Future changes to selection SQL structures must migrate both public and existing workspace schemas in the same database migration. Use the catalog IDs to enumerate schema names, quote identifiers, and perform all DDL transactionally; do not recreate workspaces or copy records. New workspace provisioning then clones the updated public structure. PostgreSQL backup/restore must include all schemas, the catalog and the token registry.

Validation: `tests/integration/project-tables.ts` runs against a disposable localhost database and exercises the real Nest HTTP stack, including cross-table writes, duplicate claims, concurrent sync, filters, presence, protection, images, public sharing and module permissions. `tests/e2e/project-tables.spec.ts` checks creation, empty data, editing, refresh, settings isolation and read-only UI.
