# MVP_SCOPE · 阶段范围与验收

## 1. 范围冻结

本次启动开发目标是 Phase 0 + Phase 1。原对话中的销售驾驶舱、完整采购计划、履约等属于产品愿景，不自动进入本次 MVP。

| 能力 | Phase 1 必做 | 暂不做 |
|---|---|---|
| 工程 | Monorepo、前后端、PG/Redis/BullMQ、Compose、迁移、检查脚本 | 微服务、Kubernetes |
| 权限 | 登录/退出、用户与角色维护、后端权限检查 | SSO、多租户、复杂审批流 |
| 商品 | SPU/SKU 创建编辑查询归档；品牌/品类基础字典 | 复杂 PIM、图片处理平台、导入导出中心 |
| 供应商/仓库 | 基础 CRUD、停用、关联校验 | 供应商门户、仓库作业系统 |
| 库存 | 按仓余额、可售计算、全仓汇总、流水、带原因调整 | 销售锁定/发货扣减、调拨、自动盘点 |
| 建议 | 纯算法、输入快照、生成/查看/接受/改量/忽略/转 PO | AI 预测、配码优化、自动下单 |
| 采购单 | 草稿/提交/确认/整单取消、明细与有效在途 | 独立采购计划实体、生产和物流跟踪 |
| 入库 | 一 PO 多 Receipt、正常分批过账、事务及幂等 | 异常入库结清、采购退货、冲销 |
| 审计 | 主数据/权限/采购/库存变化可追溯，查询页 | 财务总账和结算 |
| 前端 | 对应真实 CRUD 和操作页面 | 销售/经营大屏优先开发 |
| VOP | 独立接口、禁用模式、测试适配样例 | 真实鉴权、自动同步、回写平台库存 |

采购建议第一阶段用可替换 SalesMetricsProvider；开发/测试提供明确标识的 fixture。生产默认返回 UNAVAILABLE，不提供虚假的销量。无需真实 VOP 即可通过 fixture 走完整建议验收；生产无销量时仍可手工创建 PO。

## 2. 第一阶段用户路径

1. 管理员建立商品运营、采购员、采购经理、库存人员，并分配相应权限。
2. 建供应商、仓库、品类、品牌；创建一个 SPU 及两个颜色/尺码 SKU。
3. 通过有原因的期初调整产生初始库存和流水，不能 seed 直接塞非零余额而没有流水。
4. 在开发 fixture 下生成建议，展示数据来源和参数；接受或修改数量，转为草稿 PO。
5. 采购员提交，采购经理确认；草稿/待确认不计在途，确认后计入。
6. 库存人员建立部分正常入库单并过账；库存增加、在途减少，PO 为部分入库。
7. 重试同一入库单，结果不变；再次入库剩余数量，PO 自动完成。
8. 从库存流水和审计返回源单据，核查操作者、时间和变化前后值。

## 3. 可执行验收案例

| 编号 | 输入/动作 | 预期 |
|---|---|---|
| A01 | 未登录查询业务；采购员直接调用确认接口 | 分别 401、403，无业务写入 |
| A02 | 无 VOP 配置建商品/SKU/PO | 全部可用；无外部网络调用 |
| A03 | 期初 physical=30；reserved=damaged=0 | available=30，可由调整流水重建 |
| A04 | fixture：7日销量70，目标21天，可售30，有效在途20 | 建议160，快照保存，界面标记测试数据 |
| A05 | 建议160，人工接受150再转 PO | 原建议160保留，actual_purchase_qty=150，单据关联唯一 |
| A06 | PO100 草稿→待确认→确认 | 在途分别0、0、100 |
| A07 | 在 A03 库存上，A06 PO 第一次合格入库40 | physical=70；PO received=40；在途60；PARTIALLY_RECEIVED |
| A08 | 对 A07 重复点击、超时重试、换幂等键再过账同单 | physical仍70；该 ReceiptItem 只有一笔入库流水 |
| A09 | 再合格入库60 | physical=130；received=100；在途0；COMPLETED |
| A10 | 两张入库单并发各收70，PO剩余100 | 最多一张成功；另一张冲突；累计不超过100 |
| A11 | 写流水/写审计时注入异常 | 余额、PO、Receipt、流水、审计均回滚 |
| A12 | 同幂等键不同请求体 | 409 IDEMPOTENCY_CONFLICT，无额外写入 |
| A13 | 无销量 vs 已知销量0 | 分别“暂无销售数据”和“无近期销量”，不能混淆 |
| A14 | 已过账单 PATCH 或取消 | 拒绝；无数据变化 |
| A15 | 次品2/合格158的160到货单 | 可保存；B01未定时过账返回 BUSINESS_RULE_PENDING；不改库存 |
| A16 | 同 SKU 在两个仓库有余额 | 分仓准确、全仓仅求和一次；建议不重复扣在途 |

A04 的在途20与 A06 的PO100是独立测试场景，不共享数据。A07–A09 是连续案例。

## 4. 后续阶段

- Phase 2：标准销售订单/明细、取消/退货、SKU 销售、颜色×尺码矩阵、覆盖天数和补货计算接入可信销售数据；先确认销量和库存事件口径。可以先做受控标准数据导入，不能直接猜 VOP 字段。
- Phase 3：获得真实文档和权限后，逐项接入 VOP。OAuth/令牌方式以实际文档为准。按商品、订单、取消、退货、库存等能力分别开关；JIT/JITX、物流、档期按实际授权决定。
- 后续独立评估：采购计划、供应商门户、财务结算、自动调拨、预测优化、多平台、多租户。

## 5. 禁止事项

不得擅自扩展 MVP；不得换掉指定技术栈；不得把演示数据用于生产决策；不得直接改余额或用状态 PATCH 绕过命令；不得用 Redis 锁代替数据库约束；不得删除已参与业务的 SKU/单据；不得修改或删除历史流水；不得把 AppSecret/Token 返回前端、写进仓库或日志；不得以猜测的 VOP 响应构建真实适配器；不得未运行检查却报告“已通过”。
