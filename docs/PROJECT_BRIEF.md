# 唯品会服装供应商经营管理系统 · 项目简报

版本：v0.1 · 整理日期：2026-09-12 · 状态：可用于工程启动，待确认项按门槛隔离。

## 1. 来源与解释顺序

依据用户本次要求，以及《前端设计框架趋势》对话中产品蓝图、商品/库存/采购/销售页面、核心实体、PostgreSQL v0.1 和软件架构讨论整理。对话标识：`6aa55305-4a9c-83ec-a2a6-cc55106ffbe9`。已补读最近 10 轮相关设计；本包不依赖早期附件图片，也不宣称核实了 VOP 官方接口。

规范优先级：用户本次明确要求 > 对话后期明确收口的方案 > 早期示意设计。早期提到的约 22 个页面不是本次第一阶段全部交付范围。

本包使用三种标签：

- **已确定**：用户指定或对话收口的业务/架构原则，不得擅自替换。
- **工程默认**：为使规格可执行而补充的可逆实现约定，不冒充用户已确认的业务规则。实施时记录在 `docs/DECISIONS.md`，可在不破坏已确定原则的情况下说明理由后调整。
- **TODO**：尚未确定的外部能力或业务规则。不得猜测；只阻塞相关功能，继续其余工作。

字段/接口中未在对话逐字规定的校验、分页、会话和并发细节均属于工程默认。具体依赖小版本并未冻结，开工时核对兼容性并提交锁文件；不得自行把 Ant Design 6 降级或更换技术栈。

## 2. 产品目标（已确定）

面向唯品会服装供应商，把商品、SKU、库存、销售、采购与入库串起来，回答：什么卖得好、还剩多少、应否补货、补多少、何时缺货。

当前单平台为唯品会，服装颗粒度为款号/SPU → 颜色 × 尺码 → SKU。Product 就是 SPU；SKU 是库存与业务明细的最小颗粒度。供应商档案指上游采购供应商，不自动等同于本企业的 VOP 授权账户。

完整链路：`Product/SPU → SKU → Inventory → Sales → PurchaseSuggestion → PurchaseOrder → Receipt → InventoryTransaction → Inventory`。这表示业务联系，不表示每次采购前必须存在销售订单。

第一阶段完成内部商品与采购库存闭环，不依赖真实 VOP。Sales 在第一阶段保留标准数据源接口及测试数据，正式销售、取消/退货和分析属于 Phase 2；真实 VOP 属于 Phase 3。

## 3. 已确定技术栈

| 层 | 选型 |
|---|---|
| 工程 | Monorepo、TypeScript、Docker Compose |
| 前端 | React、Vite、Ant Design 6、TanStack Query、Zustand |
| 后端 | NestJS 模块化单体，REST `/api/v1` |
| 数据 | PostgreSQL，migration 管理结构演进 |
| 异步 | Redis + BullMQ，独立 Worker 进程复用后端模块 |
| 第三方 | 独立 `integrations/vip`，Client + Adapter + Sync |

ORM 在原对话中仍为 Prisma/Drizzle 二选一，未确认具体选型。工程默认选 Prisma；开始数据库实现前核实当前版本与 PostgreSQL、NestJS 的兼容性并写决策。需要 ORM 不支持的检查约束、索引或行锁时使用受版本管理的 SQL，不得弱化数据约束。

## 5. 第一阶段成功标准

用户能登录，在后端 RBAC 约束下建立商品、SKU、供应商和仓库；查看库存及流水；生成并处理可追溯的采购建议；创建、提交和确认采购单；分次正常入库；库存、有效在途、采购累计量和审计一致。重复入库请求不能增加第二次库存。

没有销售数据时必须显示“暂无销售数据”，不能把未知销量作为零销量产生貌似有效的补货建议。开发/测试样例必须明确标识，不能伪装成真实经营数据。
